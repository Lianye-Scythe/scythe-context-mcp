# Release Process

This project publishes through GitHub Actions after a `vX.Y.Z` tag is pushed. The publish workflow verifies the package, skips npm publishing if that exact version already exists, and creates a GitHub Release from `CHANGELOG.md`.

## Preconditions

- Work from `main`.
- The worktree must be clean.
- npm must have the GitHub Actions Trusted Publisher configured for this repository and `publish.yml`; see [Contributing](../CONTRIBUTING.md#release). The workflow publishes through OIDC.
- Do not include `.env`, `.scythe-context/`, `.repo-beacon/`, `local/`, API keys, proxy tokens, or private reference files.

## Prepare a Patch Release

```bash
git checkout main
git pull origin main
npm run release:prepare -- patch
```

The release prepare script updates:

- `package.json`
- `package-lock.json`
- `src/cli.ts`
- `CHANGELOG.md`

Review the generated changelog section before committing. It should explain behavior changes from a user or maintainer perspective, not only list implementation details.

## Verify Locally

Run the standard release checks:

```bash
npm run verify
npm run bench:gate
```

When API usage is acceptable and `GEMINI_API_KEY` is configured, also run:

```bash
npm run bench:gate:hybrid
```

`npm run verify` includes tests, build, `node scripts/bin-mode.mjs check`, CLI smoke, production audit, and `npm pack --dry-run`. If a tarball is left in the repo root after local checks, remove it before committing.

## Check the user workflow

Passing unit tests does not establish that the Skill covers the complete workflow. For changes to retrieval or embedding behavior, check these before tagging:

- Direct read / `rg` / keyword / hybrid routing, including first-time vector creation and updates after edits.
- Missing indexes, no matching vectors, limited/partial coverage, vector reuse, source deletion, and API failures with metadata still usable.
- Endpoint/model/dimension changes: status and retrieval must select the same embedding set.
- CLI credentials in the actual execution environment; MCP server environment settings do not automatically apply to CLI. Never include credentials or local indexes in packages.
- A small real-provider flow when provider compatibility changes and usage is authorized; distinguish that result from tests using a local fixture endpoint. Skill validation does not prove an agent will always make the best routing choice.
- Published package version, CLI binaries, Skill content, and three README languages. A separately installed Skill is not upgraded by updating the npm package.

Record the checked behavior and remaining limits, without claiming that all possible bugs or agent decisions are covered. If a maintained audit record exists, link it from the documentation index.

## Commit, Tag, and Push

```bash
git add package.json package-lock.json src/cli.ts CHANGELOG.md
git commit -m "Release X.Y.Z"
git push origin main
git tag vX.Y.Z
git push origin vX.Y.Z
```

Pushing `main` runs CI. Pushing the tag runs the publish workflow.

## Confirm Publication

```bash
gh run list --limit 5
gh release view vX.Y.Z
npm view scythe-context-mcp version
```

The expected result:

- CI succeeds on `main`.
- Publish succeeds on the tag.
- GitHub Release exists for `vX.Y.Z`.
- npm reports the new version.

## Reruns

The publish workflow is intentionally rerun-safe:

- If `scythe-context-mcp@X.Y.Z` already exists on npm, npm publish is skipped.
- If the GitHub Release already exists, release creation is skipped.
- The tag version must still match `package.json`.

## Release Notes

GitHub Release notes are generated by:

```bash
node scripts/release-notes.mjs X.Y.Z
```

The script extracts the matching `CHANGELOG.md` section and promotes `###` headings to `##` headings for GitHub Release formatting.
